# Audio Matrix: стабильный граф, реальные регуляторы и панель GNOME — отчёт реализации

Дата: 2026-10-21. Ветка: `fix/audio-matrix-stability` (worktree `../audio-matrix-stability`).

## Что реализовано

### Конфигурация и профили (план §2)
- Схема поднята до **11**. Миграция разделена: legacy `<10` по-прежнему архивируется и пересобирается в один профиль `main`; путь `10 → 11` только добавляет недостающее и ничего не пересоздаёт.
- Миграция `10 → 11` сохраняет идентификаторы профилей/маршрутов/нод/связей, `selected_route_id`, `active_profile`/`active_route`, пользовательские уровни и mute, фильтры, группы, закрепления, раскладку холста, сохранённые копии и существующий `migration_archive`. Удалённые технические закрепления переносятся в `migration_archive.presentation_archive`.
- Свежая конфигурация содержит ровно один профиль `{id: main, name: Основной}`; селектор профиля виден в JavaFX и в GNOME всегда, даже с одним профилем.

### Генераторы, динамические экземпляры и иерархия (план §3)
- `DynamicGeneratorNode` — управляющий (control-plane) узел: реестры `applications`, `outputs`, `browser_tabs`, шаблоны `default-application` (Source→Gain), `default-output` (Gain→Output), `default-tab` (Source→Gain), `connect_to`, `initial_gain`, `auto_pin`, `group_id`, `retain_on_disappear`, `restore_on_reappear`, `excluded_selectors`, `instances`.
- `DynamicInstanceRegistry.reconcile(...)` возвращает `ReconcileResult(configuredGraph, effectiveGraph, instances, generatedSubgraphs, configChanged)`. Развёрнутые экземпляры — настоящие узлы эффективного графа; идентификаторы детерминированы (генератор + стабильный ключ + роль), `instances` дают состав ролей, `compositeId`, доступность, достоверность и runtime-привязку.
- Стабильные ключи: `app:<applicationId>`, `process:<processName>`, `device:<DeviceIdentity fingerprint>`, вкладка — браузер + instance/profile + session token (временный tab ID идентичностью не служит).
- Перекрывающиеся выходы: обычный `device:*` и haptic `device:role:haptic_output` взаимоисключающи; одна физическая единица не получает две ветви. ESS (`io.github.ilyaandreev05.eventsoundstudio`) и собственные потоки Audio Matrix исключаются всегда.
- `GraphSubgraph` получил `parent_id` и маркер владельца-генератора: группы генерируемых экземпляров вкладываются друг в друга, циклы и конфликты членства запрещены, удаление группы-владельца запрещено — её жизненным циклом управляет реестр экземпляров.

### Маршрутизация, громкость и реальные регуляторы (план §4)
- Статическая топология (шины, рёбра, идентичность выхода, карта каналов, фильтры) отделена от динамических привязок и уровней: появление/исчезновение потока больше не меняет топологию и не вызывает полную перестройку.
- Пересборка заменена покомпонентным согласованием: у каждой ветви собственные процессы и связи; изменение одной ветви не трогает остальные, ошибка ветви изолирована и откатывается только для неё.
- Убраны исключения по именам `octine-*`; решения принимаются по семантике узла и маршрута.
- Громкость приложения применяется ровно один раз — к реальному потоку через общий resolver правил; уровень выхода устройства управляет только физическим sink; промежуточные Gain остаются программной громкостью маршрута. Абсолютные команды громкости сериализуются по цели и схлопываются: последняя принятая команда побеждает, старый обработчик не может дописать поверх неё.
- Монитор Sink больше не считается «приложением»: `Stream/Output/Audio`-монитор известного sink исключён из потока приложений (иначе монитор замыкал бы маршрут на себя).

### Merge → MultiSwitch → выходы и независимые события (план §5)
- Один генератор приложений → один Merge → ровно один MultiSwitch с одним входом; выходы — динамические `Volume→Output` по точной `DeviceIdentity`.
- Состояние выбора хранится в `RouterNode.activeLinks`; новый выход по умолчанию выключен, известный и надёжно опознанный HDMI выбирается автоматически при первом обнаружении, последующие появления сохраняют выбранное состояние и идентификаторы.
- ESS остаётся отдельной ветвью: собственная шина, собственные уровни, собственный путь к haptic-выходу; он не попадает в общий Merge приложений.

### Java ↔ GNOME (план §6)
- API **v5**, metadata расширения **20**, D-Bus кортежи `Command (ussss)` / `Result (usss)` не изменены.
- State несёт `stateEpoch` (UUID жизни моста), монотонный `stateSequence`, `profiles`, `activeProfileId` и `commandAcks` (до 128 последних `{requestId,target,property,status,value,stateSequence}`). `revision` остаётся отпечатком конфигурации.
- Команды сериализованы; завершение команды происходит только после подтверждения бэкенда, awaited `ConfigStore.updateAsync()` и публикации State с ACK. `Result` — только транспортное уведомление.
- Клиент GNOME держит pending-намерение по полной цели и свойству, принимает ACK только из принятого State, игнорирует `Result`, корректно обрабатывает устаревший/переупорядоченный ACK, ошибку, таймаут и смену epoch; request ID имеют вид `<clientUUID>:<requestUUID>`.

### Панель GNOME (план §7–§8)
- Расширение встроено в штатные Quick Settings: системные элементы не заменяются, стили и темы сохраняются, доступность и клавиатура работают.
- Один постоянный scroll-контейнер с keyed-строками: структурные изменения не пересоздают меню, сохраняются фокус, раскрытие и якорь прокрутки.
- MultiSwitch показан inline-карточкой с точными идентификаторами `activeLinks`; все route-строки участвуют в обновлении индексов.
- Закрепить можно любой сохранённый узел, Composite и сгенерированный экземпляр (`(route_id, node_id, instance_key)`); явный закреплённый endpoint Gain больше не отбрасывается. Редкие индивидуальные настройки хранятся в `instances[].overrides` генератора, второй склад закреплений не создан.
- Группы создаются, переименовываются, переупорядочиваются и удаляются с безопасным переносом элементов; граф при этом не меняется.

### Вкладки браузера (план §9)
- Firefox: опциональные адаптер и native host предоставляют метаданные вкладок и команды mute/unmute; для общей громкости браузера Firefox остаётся обычным PipeWire-приложением. Независимой PCM-громкости на вкладку нет, поэтому UI не показывает регулятор громкости вкладки.
- Chrome: owner-only Unix-сокет `$XDG_RUNTIME_DIR/audio-matrix/browser.sock` (родитель 0700, сокет 0600, без TCP), протокол JSONL v1, лимит строки 1 MiB, без URL. Сокет необязателен для захвата: захват идёт и без Audio Matrix, недоступность моста показывается явно, при появлении моста snapshot переигрывается.
- Захват привязан к `captureStreamKey` и точному имени узла `audio-matrix-chrome-<key>`; работа вкладки 512 фреймов (10,7 мс при 48 кГц) с ограниченной очередью в 4 чанка; перегрузка завершает захват явной ошибкой, а не растёт в задержку.
- Общий уровень Chrome и уровень вкладки хранятся раздельно и перемножаются при применении к реальному потоку.

### Редактор графа (план §10)
- Трёхколоночный SplitPane: палитра и дерево генераторов, холст, инспектор выбранного узла с реальной привязкой, уровнем, маршрутами и свойствами закрепления GNOME.
- Раскладка: Source+Volume → Merge → MultiSwitch → Volume+Output, отдельная нижняя дорожка ESS; карточки 220 px, колонки 80 px, строки 24 px; ручные координаты, зум, панорама и выделение сохраняются, добавлены «Упорядочить» и подгонка по содержимому.
- Диагностика показывает отдельно наличие логического узла, устойчивую привязку, выбранность/фактическую связь маршрута и измеренный сигнал (или честное «не измерено»).

### Задержка событий около 300 мс: границы доказательств (уточнение 22.10.2026)

Сообщённая пользователем задержка событий сохраняется как исходный факт. Старое объяснение её временем подтверждения `setRouteEnabled` (520 мс против 40 мс у команды конфигурации) было необоснованным: задержка управляющей команды и задержка уже работающего PCM-тракта — разные измерения. Стабильные идентификаторы узлов также не доказывают малую задержку PCM.

В соседнем Event Sound Studio обнаружен конкретный локальный дефект: `LinuxPipeBudget` вызывал возвращающий `int` `fcntl` через `MethodHandle.invokeExact` без получения результата. Для signature-polymorphic вызова это означает ожидаемый `void`, приводит к `WrongMethodTypeException`, а общий обработчик исключений скрывал неудачу ограничения pipe. Исправление и проверку фактического `F_GETPIPE_SZ` выполняет отдельная задача Event Sound Studio. 65536 байт PCM при 48 кГц, stereo s16 — 341,3 мс ёмкости; это возможный накопленный запас, а не утверждение, что любой pipe всегда добавляет такую задержку.

На стороне Audio Matrix:

- PCM обрабатывает PipeWire, а не очередь Java. `-l 10` у `pw-loopback` — запрос, не измеренная задержка; складывать запросы узлов как готовый результат нельзя. Явный `delay_ms` и lookahead включённого лимитера действительно задерживают сигнал и должны учитываться для конкретного пути.
- Debounce 250 мс у снимков PipeWire относится к обнаружению/управлению. Постоянный монитор `audiomatrix_events` уже связан с событийной шиной, поэтому очередное короткое событие не должно ждать этого снимка. Подпись динамических привязок теперь игнорирует такие ESS-потоки при наличии монитора и игнорирует служебные звуки оболочки, которые планировщик всё равно не маршрутизирует. Замена самого монитора по runtime ID остаётся причиной переподключения; при отсутствии монитора сохраняется прежний прямой ESS-путь.
- Наблюдения backend и записи громкости/mute выполняются одной последовательной управляющей очередью. Старый снимок больше не может завершиться после следующей записи и ошибочно откатить опубликованный уровень. Длительные измерения/калибровка не занимают эту очередь.
- В fallback-переносе потока убран `pw-link --wait`: этот ключ удерживает клиент работающим, а не подтверждает создание связи. Это исправление управляющего пути, не заявленное объяснение задержки событий.

### Безопасное измерение действующего маршрута

Команда smoke выполнена успешно в отдельной приватной PipeWire-сессии без доступа к физическим ALSA/BT-узлам:

```sh
python3 scripts/pipewire-route-smoke.py
```

Скрипт создаёт отдельные HOME/XDG/`PIPEWIRE_RUNTIME_DIR` в `/tmp`, приватный core и policy-only WirePlumber, без доступа к физическим ALSA/BT-узлам и без изменения пользовательских сервисов/настроек. Опциональный `AudioMatrixEventLatencyLiveSmokeTest` компилирует настоящий fixture графа и держит `PipeWireRouteManager` активным во время измерения: ESS-проигрыватель → `audiomatrix_events` → событийная шина → маршрут → приватный выход. Путь проверяется по реальным связям; прямой обход проигрыватель → выход запрещён.

Два отвода записываются одним двухканальным `pw-cat`: FL — монитор `audiomatrix_events`, FR — монитор приватного выхода. Разность номеров кадров одинаковых импульсов даёт p50/p95/max **добавки маршрута от входного монитора до выходного**, без ошибки от времени flush/размера файла или разных часов двух рекордеров. В текущем smoke app gain — 0,500, event gain — 0,250; app/event cross-leakage — 0,0000/0,0000; surviving branch — 0,1000→0,1003. По 7 event impulse samples routed event latency p50/p95/max составила 0,00 мс от входного монитора `audiomatrix_events` до монитора приватного выхода; xrun delta — 0. Это только route latency: измерение не включает путь от input device/evdev через ESS до физического выхода, DAC, усилитель, тактильный преобразователь или Bluetooth.

Старый прямой `latency_probe` удалён. Скрипт принимает только JSON нового одновременного измерения и обозначает результат как `routed_event_latency_ms_*`; текущий результат приведён выше. Сборка, тесты и изолированные smoke-проверки выполнены успешно (см. таблицу); эта метрика не является сквозной задержкой до физического тактильного выхода.

Загруженный модуль расширения GNOME Shell кэшируется до конца сеанса, поэтому исправленный JS вступает в силу только после перезахода в сессию.

## Ограничения

- Опциональная интеграция Firefox предоставляет метаданные вкладок и mute/unmute; независимых захвата и PCM-громкости на вкладку нет, поэтому регулятор громкости вкладки отключён.
- Захват вкладки Chrome требует жеста пользователя и разрешений расширения; Audio Matrix их не выдаёт и не включает расширение автоматически.
- В текущих проверках не использовались физические аудиоустройства и не выводился реальный звук или тактильный сигнал; старые наблюдения живой маршрутизации выше относятся к отдельным прежним прогонам. Отдельный физический 200 Гц smoke на усилителе не выполнялся.
- Измерение PipeWire ограничено монитором входа `audiomatrix_events` и монитором приватного выхода; оно не охватывает input device/evdev → ESS → физический выход, DAC, усилитель, haptic transducer или Bluetooth.
- Скриншот изолированного headless GNOME Shell 50 smoke сохранён и просмотрен в `/tmp`; он не является скриншотом пользовательского live-сеанса и не подтверждает live-host integration.
- Установка пакетов в пользовательскую систему, включение расширения в пользовательском сеансе и выход из сеанса/перезапуск GNOME не выполнялись.
- ZIP `build/Audio-Matrix-GNOME-install.zip` проверен: размер 160,028,376 bytes, SHA-256 `5919c968d086c71ac51028747efb7f445821b4d4c2ed5e4dca84907dee7d678b`. `unzip -t` прошёл; `unzip -l` подтвердил ровно три элемента в корне: `audiomatrix_0.4.1_amd64.deb`, `eventsoundstudio_0.2.4_amd64.deb`, `INSTALL.txt`.

### Дефект пустой группы «Приложения» в панели GNOME (21.10.2026)

Пользователь сообщил, что группа «Приложения» в Quick Settings пуста, хотя на машине идут Chrome, Firefox, gnome-shell, wireplumber и pw-cat. Опубликованное состояние содержало приложения, но закреплённый генератор `octine-main-source` (реестр `applications`, селектор `application:unassigned`) публиковал пустой список.

| Дефект | Симптом | Исправление | Регрессия |
|---|---|---|---|
| Список закреплённых приложений фильтровался по селекторам узлов *эффективного* графа | материализованные реестром экземпляры генератора (узлы-источники с селекторами `process:chrome`, `application:…`) считались «явными заявками» и исключали ровно те приложения, которые генератор обслуживает; у каждого живого приложения есть правило в `applications[]`, поэтому группа оставалась пустой | заявками считаются только узлы, созданные пользователем в графе: материализованный экземпляр генератора больше не заявляет приложение; уровень приложения публикует его владелец — сохранённое правило `applications[]`, а для приложения без правила — сгенерированный экземпляр; поток Event Sound Studio не попадает в общий список приложений | `GnomeBridgeStateBuilderApplicationsTest` — на старом коде падает (группа «Приложения» пуста), на новом публикует оба приложения с их уровнями и не публикует поток событий |
