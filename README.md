# Audio Matrix

A PipeWire mixer and routing workspace for Linux. The app stores settings in `~/.config/audio-matrix/config.yaml` and talks to the user's existing PipeWire/WirePlumber session.

## Run

Use Java 25 and `./gradlew run`. Build a local Debian package with `./gradlew packageDeb`; it appears under `build/deb/`. See [docs](docs/) for configuration and backend limits.

For GNOME Quick Settings, run `scripts/install-gnome-quick-settings.sh`, sign out and back in so GNOME Shell discovers the extension, then enable `audio-matrix-quick-settings@ilyaandreev05` in GNOME Extensions. The panel can select the output, profile mode, active route channel map, mute, or open the full app. Audio actions remain in the Java application and use its current PipeWire session; controls are disabled when the Java bridge is unavailable.

Routes can be applied explicitly and are restored on Clear or application exit. Audio Matrix-owned route gains ramp down/up over `engine.transition_ms` (0–1000 ms) when rebuilding a graph. App, bus, route, global, and output EQ chains use PipeWire filter-chain biquads; each matched stream gets a separate app-EQ node. High-pass and low-pass filters support 6, 12, 18, 24, 36, and 48 dB/oct. Steeper orders use cascaded Butterworth sections; the Q control applies to the 12 dB/oct form. After branches to one sink are mixed, output EQ and a linked lookahead peak limiter run as separate stages. Limiter settings are available on the DSP page and saved in YAML; the default ceiling is −1 dBFS with 5 ms lookahead and 50 ms release. The effects master controls Audio Matrix routes only. The limiter caps digital peaks, not amplifier or transducer power. The DSP page reads peak/RMS from the selected PipeWire sink monitor without storing PCM; input metering is opt-in and stops when the page is closed. A temporary B mode bypasses EQ, retains the limiter/polarity, and attenuates routes by a conservative positive-EQ gain bound. Headroom is a full-scale model, not a voltage, acoustic SPL, watt measurement, or perceptual loudness match. Haptic routes require source paths only from an `effects` bus and an explicitly tagged `haptic_output`; Subwoofer requires a `subwoofer` branch/output with only music or subwoofer roots and warns when any active path lacks low-pass; Speaker requires a `speaker` output role. Hybrid keeps selected routes, while Multi-output warns unless at least two physical outputs are routed. These mode policies have unit coverage but have not been checked against a live or physical haptic graph. Measured filter response remains unfinished.

The Profiles page exports and previews a full ZIP backup of YAML configuration, routes, profiles, and referenced calibration files. Import requires confirmation; matching volume/mute rules may apply immediately, an active route graph will refresh, and imported `apply_on_start` may apply routes immediately. Missing or ambiguous devices can be mapped or kept offline; see [backup format](docs/backup-format.md).

The Devices page lets you assign a display name and stable selector to a sink or source. Profiles and routes refer to saved device IDs; matching uses node name or description rather than transient PipeWire IDs. Offline saved selectors remain visible for remapping. Saved output volume and mute rules are applied when a matching sink reconnects.

The Routes page edits buses and bus-to-bus or bus-to-output routes, then provides explicit Apply and Clear controls for the PipeWire graph. Channel maps include stereo, swap, mono/front selection, center and LFE extraction, and rear/side/surround/all-to-mono presets. Routes can also use a user-authored signed coefficient matrix of up to 8 inputs × 8 outputs. Matrix inputs must match the source bus layout; outputs must exist on the destination, and a row whose absolute coefficients sum above 1 requires the output limiter. Negative coefficients invert that input's phase before mixing. The validator also rejects feedback cycles and missing `filters_ref` chains. The matrix graph passed an opt-in PipeWire startup check with two temporary, unconnected endpoints; no live route or playback stream was created. A live digital-silence check confirmed the virtual-sink/route-loopback path, output EQ followed by a single linked limiter, fallback to the system output, idempotent apply, and restoration of original links on close. The native limiter harness also verifies its digital ceiling and linked-channel attenuation. A muted, zero-volume HDMI monitor smoke confirmed live digital metering without changing the sink's volume or mute. The temporary A/B config transformation and role-based mode policy have unit coverage, but live A/B and specialized-mode graph checks have not been run. Filter response has not been acoustically measured. The backend refreshes and rebuilds active routes after PipeWire monitor reconnects; an isolated private-daemon restart smoke passed under `/tmp`. Restarting the user's system service, hardware unplug fallback, smooth transitions under load, and latency/stress remain unverified.

To check route-graph reconstruction, run `AUDIO_MATRIX_LIVE_PIPEWIRE_SMOKE=1 ./gradlew test --tests io.github.ilyaandree05.audiomatrix.audio.PipeWireChannelMatrixRouteLiveSmokeTest --no-configuration-cache --no-daemon`. The smoke forces `reapplyAfterReconnect` through a signed-matrix route into a temporary null sink at 0 route volume and with no application streams; it checks that the graph links return and that default sink ID/volume/mute stay unchanged. This checks graph reconstruction on the current server; the separate private-daemon smoke above checks backend snapshot recovery after a daemon restart.

The Calibration page includes gated manual tone, impulse, and stepped-sweep checks for the selected output. The impulse is a Hann-shaped 10 ms, 100 Hz stereo pulse capped at 0.005 PCM peak and `pw-play` volume 0.03; all three controls remain disabled until the hardware path is acknowledged, and each requires a confirmation naming the selected output. This is a listening check, not a measurement, and an unknown amplifier can add gain. The page can also analyze an existing mono/stereo 16-bit PCM WAV from a microphone or accelerometer recording made during the selected stepped sweep. Importing a WAV is offline and does not open audio devices. The “Estimate sweep start” action searches the first 10 seconds for the requested logarithmic tone sequence, reports fit quality and offset uncertainty, and refuses weak or repeated matches; review or adjust the suggested offset before plotting. An imported sensor WAV can also be analyzed as an impulse ring-down: set an impulse offset and response window, then inspect the 10 ms envelope, integrated energy-decay curve, measured T20 segment, extrapolated T60, dominant mode, and a Q estimate derived from the decay slope and mode frequency. At least 20 ms of pre-roll is required; ambiguous/no-response files are rejected. The original WAV and time-domain decay CSV are separate files referenced from YAML and full-backup ZIPs. These are unverified relative signal estimates with no physical sensor units. An optional synchronized capture explicitly targets a selected PipeWire input and output, records 48 kHz PCM, and plays a short sweep at 0.025 PCM amplitude and `pw-play` volume 0.10. It requires output-chain and sensor-mount acknowledgements plus a second confirmation; the device volume is not changed, and the capture stays in a temporary file until saved. The saved profile records the source node name and description. Verify the amplifier, load, wiring, and physical gain before confirming. The sweep's capture offset starts at 500 ms and can be adjusted. The page plots relative input level on a logarithmic frequency axis, provides an exact-values table, and saves the original WAV and response CSV as separate files referenced from YAML and full-backup ZIPs. Saved curves from the same output, source, method, channel, and sensor position can be overlaid with a delta table. Since each curve is normalized to its own median, this comparison shows response shape rather than absolute vibration or overall level. The plot has no physical sensor units; imported and captured measurements remain unverified. The optional advisor proposes at most three negative peaking-EQ cuts, each no deeper than 3 dB, only for clear interior peaks on unclipped curves; it never boosts response nulls. It shows a median-normalized offline prediction first. Applying requires a saved WAV, the same selected output, hardware-path acknowledgement, and an output-specific confirmation; the filters are stored in a dedicated device chain linked from the calibration record. A rollback restores the previous chain reference and persists across sessions in YAML when you reopen the saved curve. Applying the config still does not verify acoustic or vibration response.

## Verification

Run the regression suite with `./gradlew test --no-configuration-cache --no-daemon`. To check independent Chrome and Telegram application rules against the current PipeWire server, run `AUDIO_MATRIX_LIVE_PIPEWIRE_SMOKE=1 ./gradlew test --tests io.github.ilyaandreev05.audiomatrix.audio.ApplicationStreamRuleLiveSmokeTest --no-configuration-cache --no-daemon`. This smoke uses zero-filled WAVs and `pw-play --target 0`, so its temporary streams remain unlinked from outputs; it verifies PipeWire stream volume/mute controls, not audible playback from those applications. To verify backend reconnection without touching the current audio session, run `python3 scripts/pipewire-reconnect-smoke.py`; it starts a private PipeWire daemon under a temporary runtime directory, stops and restarts it, and checks that Audio Matrix publishes a fresh connected snapshot.
