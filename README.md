# Audio Matrix

A PipeWire mixer and routing workspace for Linux, prepared as version 0.3.0. Automatic route fingerprints exclude Audio Matrix's own virtual nodes. Route updates are coalesced while a graph is being built, and an unchanged failed graph waits for changed inputs, a PipeWire reconnection, or an explicit retry instead of repeatedly rebuilding. GNOME Quick Settings uses one scrollable column of user-defined groups containing only pinned graph nodes. Source and Output nodes are ordinary pins; app streams, device controls, and graph parameters appear inside their associated cards. Pin groups, order, and card view are presentation state and do not duplicate graph parameter values. Level changes update existing rows without rebuilding the menu. GNOME bridge API v3 includes config revisions and stable device references for output commands. Switch/Matrix selections keep stable PipeWire routes and update live levels without restarting route nodes; switches lower the old branch before raising the new one. Profiles own independent graph routes and groups, and duplicating a profile gives its graph nodes, links, groups, quick controls, and pins new IDs. Exactly one graph route is active across profiles; each profile remembers its last selected route. Deleting the active profile requires choosing a replacement route or explicitly stopping the graph. It also includes 0.2.2's per-output post-mix limiter staging and 0.2.1's virtual system sink discovery for GNOME master synchronization. The app stores settings in `~/.config/audio-matrix/config.json` and talks to the user's existing PipeWire/WirePlumber session. On first launch, it migrates `config.yaml` and preserves it as `config.yaml.before-json`; schemas 1–4 migrate to schema 5, and each schema upgrade preserves the source as `config.json.before-schema-5` (or a numbered sibling if that name already exists). The current default document is `src/main/resources/config.example.json`; `config.example.yaml` remains a migration example.

## Run

Use Java 25 and `./gradlew run`. Build a local Debian package with `./gradlew packageDeb`; it appears under `build/deb/`. See [docs](docs/) for configuration and backend limits.

For GNOME Quick Settings, run `bash scripts/test-gnome-quick-settings.sh` to check the GNOME 50 extension package. It replaces the built-in sound-output submenu while keeping GNOME's standard master slider and other Quick Settings tiles. Pinned graph nodes appear in one scrollable column of user-named groups; new routes migrate their Source and Output nodes into the initial groups, while other nodes can be pinned from the editor. Group expansion and slider values remain in place during ordinary level updates. Disabling the extension restores the original menu items and sound-menu availability. The `.deb` contains the extension files and install/restore helpers. Run `/opt/audiomatrix/bin/install-gnome-quick-settings.sh`, then enable `audio-matrix-quick-settings@ilyaandreev05` in GNOME Extensions; on Wayland, sign out and back in first. It does not add a separate Audio Matrix tile. Bridge API v3 commands carry a config revision and request ID and return an applied/error result; stale structural commands are rejected and controls are disabled when the matching bridge is unavailable.

## Chrome tab capture

The `.deb` also contains a Manifest V3 Chrome extension and a Native Messaging PCM bridge. Run `bash scripts/test-chrome-tab-capture.sh` to verify its message framing, PipeWire target, and install/rollback paths with a fake process. After reviewing the system-change plan, run `/opt/audiomatrix/bin/install-chrome-tab-capture.sh`, then load the unpacked extension from `~/.local/share/audio-matrix/chrome-tab-capture` at `chrome://extensions`. Capture starts only when you press **Capture this tab** in the extension popup. The selected tab is temporarily captured and its audio enters the `audiomatrix_system` virtual sink as the stable application `io.github.ilyaandree05.audiomatrix.chrome-tab-capture`; Audio Matrix can route that source and the GNOME mixer shows its individual PipeWire streams. If the virtual sink is absent, the bridge does not fall back to a physical output. Stopping capture or closing the tab closes the media stream, restoring normal Chrome playback. The extension shows open tab names locally for selection, but sends no URL or title to the native bridge and writes no tab identifiers into the saved graph. To roll back, remove the manually loaded extension from `chrome://extensions`, then run `/opt/audiomatrix/bin/uninstall-chrome-tab-capture.sh`; the prior extension files and host manifest are restored.

Event Sound Studio uses the isolated `audiomatrix_events` virtual sink. The `.deb` includes a user service for that sink, but installation does not enable it. After installation, start it explicitly with `/opt/audiomatrix/bin/enable-audiomatrix-events-service.sh`; disable and remove its user unit with `/opt/audiomatrix/bin/disable-audiomatrix-events-service.sh`. The sink does not become GNOME's default output, and its discard side does not autoconnect to hardware. Without the service, Event Sound Studio events stay silent rather than falling back to the current output.

Audio Matrix supports a single per-user process. Closing its editor window hides it and leaves an applied route running; launch Audio Matrix again from GNOME to reopen the editor. The package includes optional user services, but does not enable them during installation. The output helper uses `wpctl` and resolves transient PipeWire node IDs each time. After reviewing the system-change plan, `/opt/audiomatrix/bin/enable-audiomatrix-service.sh` installs a PipeWire configuration drop-in for the permanent virtual system input, restarts PipeWire to load it, and starts the engine user service. This makes the virtual sink the default; ordinary audio needs a working Audio Matrix route to be audible. The helper records the previous output and backs up replaced user units/configuration. `/opt/audiomatrix/bin/disable-audiomatrix-service.sh` stops the engine, restores the previous output and any saved user files, removes the drop-in, and restarts PipeWire. To restore the previous GNOME extension files, run `/opt/audiomatrix/bin/uninstall-gnome-quick-settings.sh`. To stop a manually launched background instance, run `/opt/audiomatrix/bin/AudioMatrix --quit`.

Routes can be applied explicitly and are restored on Clear or application exit. Audio Matrix-owned route gains ramp down/up over `engine.transition_ms` (0–1000 ms) when rebuilding a graph. App, bus, route, global, and output EQ chains use PipeWire filter-chain biquads; each matched stream gets a separate app-EQ node. High-pass and low-pass filters support 6, 12, 18, 24, 36, and 48 dB/oct. Steeper orders use cascaded Butterworth sections; the Q control applies to the 12 dB/oct form. A graph peak limiter after a mixer is compiled into that device's linked lookahead limiter stage after output mixing; route EQ stays on the signal path before the output. Limiter settings are available on the DSP page and saved in `config.json`; the default ceiling is −1 dBFS with 5 ms lookahead and 50 ms release. The effects master controls Audio Matrix routes only. The limiter caps digital peaks, not amplifier or transducer power. The DSP page reads peak/RMS from the selected PipeWire sink monitor without storing PCM; input metering is opt-in and stops when the page is closed. A temporary B mode bypasses EQ, retains the limiter/polarity, and attenuates routes by a conservative positive-EQ gain bound. Headroom is a full-scale model, not a voltage, acoustic SPL, watt measurement, or perceptual loudness match. Haptic routes require source paths only from an `effects` bus and an explicitly tagged `haptic_output`; Subwoofer requires a `subwoofer` branch/output with only music or subwoofer roots and warns when any active path lacks low-pass; Speaker requires a `speaker` output role. Hybrid keeps selected routes, while Multi-output warns unless at least two physical outputs are routed. These mode policies have unit coverage but have not been checked against a live or physical haptic graph. Measured filter response remains unfinished.

The Profiles page exports and previews a full ZIP backup of JSON configuration, routes, profiles, and referenced calibration files. Import requires confirmation; matching volume/mute rules may apply immediately, an active route graph will refresh, and imported `apply_on_start` may apply routes immediately. Missing or ambiguous devices can be mapped or kept offline; see [backup format](docs/backup-format.md).

The Devices page lets you assign a display name and stable selector to a sink or source. Profiles and routes refer to saved device IDs; matching uses node name or description rather than transient PipeWire IDs. Offline saved selectors remain visible for remapping. Saved output volume and mute rules are applied when a matching sink reconnects.

The Routes page retains the established bus-based PipeWire engine. The Graph editor stores routes, groups, inactive snapshots, typed source/output/processing nodes, connections, and Switch, MultiSwitch, Selector, and Matrix cells. Its canvas supports node dragging, direct typed-port connections, saved zoom, and a source-to-output connection matrix over the same graph. Output nodes can select front FL/FR or rear RL/RR channels on multichannel hardware, so one physical Family 17h sink can expose the green and black jacks as separately routed endpoints. The rear pair is available only when the active ALSA profile exposes four or more channels; route planning leaves that branch unapplied while the device is stereo. The compiler translates supported graph paths into the existing PipeWire route plan; Switch/Matrix alternatives keep stable route nodes and set inactive paths to zero/mute, so selecting a different wired branch updates live levels without rebuilding the route graph. A missing path, invalid port, cycle, or unsupported processor is rejected before applying. The source/output overview inserts an explicit Mixer when it adds a second source to an output. Route application remains an explicit editor action. Legacy bus-based routes are kept, and Clear restores prior PipeWire links. JSON is the live config format; YAML remains available for migration and archive import.

To check route-graph reconstruction, run `AUDIO_MATRIX_LIVE_PIPEWIRE_SMOKE=1 ./gradlew test --tests io.github.ilyaandree05.audiomatrix.audio.PipeWireChannelMatrixRouteLiveSmokeTest --no-configuration-cache --no-daemon`. The smoke forces `reapplyAfterReconnect` through a signed-matrix route into a temporary null sink at 0 route volume and with no application streams; it checks that the graph links return and that default sink ID/volume/mute stay unchanged. To verify the backend and graph across a restart, run `python3 scripts/pipewire-reconnect-smoke.py`. It starts a private PipeWire daemon, a policy-only WirePlumber instance without hardware monitors, and a temporary null sink; then it stops and restarts the private daemon and checks that the backend reconnects and the route graph is rebuilt. Neither smoke restarts the user's PipeWire service or routes to a physical output.

The Calibration page includes gated manual tone, impulse, and stepped-sweep checks for the selected output. The impulse is a Hann-shaped 10 ms, 100 Hz stereo pulse capped at 0.005 PCM peak and `pw-play` volume 0.03; all three controls remain disabled until the hardware path is acknowledged, and each requires a confirmation naming the selected output. This is a listening check, not a measurement, and an unknown amplifier can add gain. The page can also analyze an existing mono/stereo 16-bit PCM WAV from a microphone or accelerometer recording made during the selected stepped sweep. Importing a WAV is offline and does not open audio devices. The “Estimate sweep start” action searches the first 10 seconds for the requested logarithmic tone sequence, reports fit quality and offset uncertainty, and refuses weak or repeated matches; review or adjust the suggested offset before plotting. An imported sensor WAV can also be analyzed as an impulse ring-down: set an impulse offset and response window, then inspect the 10 ms envelope, integrated energy-decay curve, measured T20 segment, extrapolated T60, dominant mode, and a Q estimate derived from the decay slope and mode frequency. At least 20 ms of pre-roll is required; ambiguous/no-response files are rejected. The original WAV and time-domain decay CSV are separate files referenced from `config.json` and full-backup ZIPs. These are unverified relative signal estimates with no physical sensor units. An optional synchronized capture explicitly targets a selected PipeWire input and output, records 48 kHz PCM, and plays a short sweep at 0.025 PCM amplitude and `pw-play` volume 0.10. It requires output-chain and sensor-mount acknowledgements plus a second confirmation; the device volume is not changed, and the capture stays in a temporary file until saved. The saved profile records the source node name and description. Verify the amplifier, load, wiring, and physical gain before confirming. The sweep's capture offset starts at 500 ms and can be adjusted. The page plots relative input level on a logarithmic frequency axis, provides an exact-values table, and saves the original WAV and response CSV as separate files referenced from `config.json` and full-backup ZIPs. Saved curves from the same output, source, method, channel, and sensor position can be overlaid with a delta table. Since each curve is normalized to its own median, this comparison shows response shape rather than absolute vibration or overall level. The plot has no physical sensor units; imported and captured measurements remain unverified. The optional advisor proposes at most three negative peaking-EQ cuts, each no deeper than 3 dB, only for clear interior peaks on unclipped curves; it never boosts response nulls. It shows a median-normalized offline prediction first. Applying requires a saved WAV, the same selected output, hardware-path acknowledgement, and an output-specific confirmation; the filters are stored in a dedicated device chain linked from the calibration record. A rollback restores the previous chain reference and persists across sessions in JSON when you reopen the saved curve. Applying the config still does not verify acoustic or vibration response.

## Verification

Run the regression suite with `./gradlew test --no-configuration-cache --no-daemon`. To check independent Chrome and Telegram application rules against the current PipeWire server, run `AUDIO_MATRIX_LIVE_PIPEWIRE_SMOKE=1 ./gradlew test --tests io.github.ilyaandreev05.audiomatrix.audio.ApplicationStreamRuleLiveSmokeTest --no-configuration-cache --no-daemon`. This smoke uses zero-filled WAVs and `pw-play --target 0`, so its temporary streams remain unlinked from outputs; it verifies PipeWire stream volume/mute controls, not audible playback from those applications. To verify backend reconnection without touching the current audio session, run `python3 scripts/pipewire-reconnect-smoke.py`; it starts a private PipeWire daemon under a temporary runtime directory, stops and restarts it, and checks that Audio Matrix publishes a fresh connected snapshot.
